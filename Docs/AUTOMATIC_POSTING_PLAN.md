# 自動投稿の運用計画

## 結論

自動投稿の期間、時間帯、23件の本文採用、9月3日だけの時間帯外例外、ローカルH2と本番Neonの切替対象、既存Render URLと既存アカウントへの統一まで確定しました。2026-09-03に本番Neon全削除、同名アカウント再作成、当日1件の投稿まで利用者が承認しました。ただし、先行したRenderデプロイが試験失敗で停止したため、新しい公開版の成功と操作確認が済むまでは資格情報を使わず、`externalPostingEnabled=false`の安全状態を維持します。

## 確定している条件

- 対象期間: 2026年9月3日から2026年9月25日まで（両端を含む）
- 時刻基準: 日本標準時（Asia/Tokyo）
- 投稿時刻: 各日の10:00から16:00までの範囲でランダム
- 重複防止: 対象アカウント、対象日、投稿識別子の組で1日1件まで
- 期間外停止: 2026年9月26日以降は新しい投稿を作らない
- 費用: 有料サービス、有料枠、課金クレジットは自動利用しない
- 情報保護: 資格情報、Cookie、日記本文をGit、通常ログ、報告書へ記録しない
- 本文: 23件すべて採用済み
- 実用性の確認: 23日をまとめて模擬するだけでなく、運用開始後は毎日の実行ごとに事前条件・投稿結果・重複防止・翌日継続可否を確認する
- 時間帯外例外: 2026年9月3日だけ許可。実際の投稿日時を遡らせない
- 既存データの更新対象: ローカルH2と本番Neon。実削除は個別の復旧点・件数確認後

## 実装・運用の合格条件

- 自動投稿は初期状態で無効にし、開始・停止状態を人が確認できる
- 日ごとの予定時刻を実行前にローカルへ保存し、再起動で別時刻へ変わらない
- 同日の再実行、再起動、通信再試行で重複投稿しない
- 10:00より前、9月3日以外の16:00より後、期間外には投稿しない
- 認証失敗、接続失敗、画面変更、CSRF不一致では投稿せず安全停止する
- ログには日時、結果、影響、次の安全な操作だけを残し、本文と秘密値を残さない
- 投稿後は対象日と公開画面の成功状態を確認する。内容そのものは通常報告へ転記しない
- 毎日の実行で、当日1件、重複0件、認証・CSRF・公開画面、次回予定、停止状態を確認し、秘密情報を除いた合否だけを運用記録へ残す
- 停止方法、再開方法、失敗時の復旧方法をローカル運用資料に記録する

## 削除を伴う切替手順

1. 対象DBとテーブルを名前・場所・所有者・容量で特定する。ローカルH2は`USERS`と`DIARIES`が各0件で、DBファイル24,576 bytes、読取り前後SHA-256不変を確認済み。
2. 書込み処理を停止し、復旧点を作成して読取り復元を確認する。
3. 削除対象件数と保持対象件数を提示し、直前確認を受ける。
4. 確認された対象だけを削除する。
5. 新規データと自動投稿を隔離環境で1回検証する。
6. 外部投稿の直前確認後に有効化し、初回結果を確認する。
